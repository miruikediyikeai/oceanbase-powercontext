# Qoder 开发任务书

## 交给 Qoder 的项目背景

项目是“拾忆 Recall”，面向需要反复复习课程笔记的个人学习者。现有原型由 Codex 编写，已建立知识卡片导入、间隔复习、PowerContext 记忆保存和恢复流程。目标是在 Qoder 中完成项目的主要功能开发和验证，保留真实过程材料。所有资产写入本仓库 `qoder/`，基于 `2026-competition-ecosystem` 的后代分支开发。

## 可直接粘贴的开发需求

> 请先阅读 qoder/README.md、docs/ARCHITECTURE.md 和实际验证结果。检查当前运行行为，提出并实现一个完整的学习笔记转卡片工作流：用户粘贴 Markdown 笔记，选择主题并确认来源；系统提取或辅助生成候选问题与答案；用户逐条核对、编辑后才导入 PowerContext。需要实现笔记分段、候选编辑界面、稳定 ID、重复导入处理、错误提示和行为测试。生成模式必须使用真实模型调用，API Key 仅保存在后端环境变量，缺少模型配置时明确说明；可以提供不调用模型的手工选段模式。未确认的候选不得进入长期记忆。请记录关键设计、实现和实际运行验证，并保留 Qoder 对话截图。

> 接着实现单卡复习历史与周学习回顾。请读取 PowerContext 实际历史版本，保留精确引用，展示每次自评、下次安排与遗忘次数变化。历史不可通过当前状态伪造。周回顾统计必须说明时间范围和计算规则，没有数据时显示空状态，不能虚构使用效果。补充相应真实服务验收场景。

> 完成后检查 Windows 与 Linux 的安装步骤，运行核心测试及实际 PowerContext 验证，修复发现的问题。为项目录制一次完整演示，包含从笔记创建卡片、复习、关闭后恢复和历史回顾。根据实际功能更新 README、介绍网站和提交材料，确保描述与运行结果一致。

这些任务需要实际在 Qoder 中执行，不能把任务书本身当作开发证据。是否满足“主要开发”最终由赛事评审判定，不能用工作量比例自行保证。

## 开发证据

关键节点保留 Qoder 原始对话截图或录屏：需求拆解、主要功能实现、遇到的缺陷与修复、实际测试、Sites 发布。记录时间、任务、变更文件、运行命令和结果；注明既有 Codex 原型的范围，避免误记作者。账号 UID 从 Qoder 个人账号页面获取，填入最终提交表单，勿把账号凭据放入仓库。

## Qoder Sites 发布需求

> 请根据 qoder/site/index.html 和项目实际截图，通过 Qoder Sites 创建项目介绍网站。页面包含项目简介、痛点、核心功能、真实截图或演示视频、代码仓库、运行说明、验证证据与体验方式。不要把本地 localhost 链接当作公众体验地址，不声明未测量的节省时间或真实用户规模。使用个人账号，把可见范围设为“任何人都可访问”，发布后记录完整 URL，并在未登录浏览器中核验。

介绍网站与后端是独立交付。Sites 不自动替代本地 Python 运行环境。若部署远程体验后端，应先实现认证、学习者授权和 HTTPS，再提供公网入口；当前个人本地版只发布项目说明和评审运行入口。
